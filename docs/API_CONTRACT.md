# قرارداد API مشترک سایت و اپ — v1

آدرس پایه از `VITE_API_BASE_URL` خوانده می‌شود. در حالت remote، پاسخ‌ها JSON و همهٔ زمان‌ها ISO 8601 هستند.

## احراز هویت

- خواندن محتوای منتشرشده عمومی است.
- ویرایش محتوا و خواندن درخواست‌ها نیازمند Bearer token مدیر است.
- توکن در مرورگر، مخزن یا فایل env عمومی ذخیره نمی‌شود؛ احراز هویت باید با کوکی امن HttpOnly یا ارائه‌دهندهٔ معتبر اجرا شود.

## مسیرها

### `GET /v1/site-content`

پاسخ: شیء کامل محتوا با `brand`، `projects`، `services`، `tutorials`، `insights`، `products` و `settings`.

`brand.socialLinks` یک فهرست توسعه‌پذیر با فیلدهای `id`، `platform`، `label`، `url` و `enabled` است. شبکه‌های شناخته‌شده شامل WhatsApp، Telegram، Instagram، YouTube، LinkedIn و Pinterest هستند و مقدار `custom` اتصال پلتفرم‌های آینده را بدون تغییر قرارداد ممکن می‌کند.

### `PUT /v1/site-content`

دسترسی: مدیر. بدنه همان ساختار محتوای کامل است. بک‌اند باید schema، طول متن، نوع URL و سطح دسترسی را اعتبارسنجی کند.

### `GET /v1/projects`

پارامترهای پیشنهادی: `published=true`، `limit` و `cursor`. پاسخ:

```json
{
  "items": [],
  "nextCursor": null
}
```

### `GET /v1/projects/:id`

پاسخ: جزئیات پروژه، رسانه‌های بهینه‌شده، اطلاعات SEO و نسخهٔ سبک برای اپ.

### محتوای آموزشی و فروش

- `GET /v1/tutorials` و `GET /v1/tutorials/:slug`
- `GET /v1/insights` و `GET /v1/insights/:slug`
- `GET /v1/products` و `GET /v1/products/:slug`

همهٔ فهرست‌ها باید `published`، `limit`، `cursor` و زبان را پشتیبانی کنند. پاسخ عمومی فقط دادهٔ منتشرشده را برمی‌گرداند؛ پیش‌نویس فقط برای مدیر قابل مشاهده است.

### `POST /v1/leads`

بدنه:

```json
{
  "name": "string",
  "contact": "string",
  "projectType": "string",
  "message": "string"
}
```

بک‌اند باید rate limit، ضداسپم، رضایت حریم خصوصی، اعتبارسنجی سروری و ثبت audit داشته باشد. پاسخ موفق `201` با شناسه و زمان ثبت است.

### `GET /v1/leads`

دسترسی: مدیر. فهرست صفحه‌بندی‌شدهٔ درخواست‌ها.

### `DELETE /v1/leads/:id`

دسترسی: مدیر. حذف باید در audit log ثبت شود و بر اساس سیاست نگه‌داری داده قابل پیگیری باشد.

### `POST /v1/subscribers`

بدنه شامل `email` و نسخهٔ رضایت کاربر است. سرور باید ایمیل را نرمال، تکراری‌ها را ادغام، رضایت را ثبت و تأیید دومرحله‌ای ایمیل را پشتیبانی کند.

### `GET /v1/subscribers`

دسترسی: مدیر. فهرست صفحه‌بندی‌شده؛ ایمیل‌ها دادهٔ شخصی‌اند و در خروجی عمومی قرار نمی‌گیرند.

### `DELETE /v1/subscribers/:id`

دسترسی: مدیر. لغو عضویت و حذف طبق رضایت ثبت‌شده و الزامات حریم خصوصی انجام می‌شود.

### سفارش و پرداخت

- `POST /v1/checkout-sessions` — ایجاد پرداخت فقط روی سرور و بر اساس شناسه و قیمت ثبت‌شدهٔ محصول
- `POST /v1/payments/webhook/:provider` — دریافت رویداد امضاشدهٔ درگاه
- `GET /v1/orders/:id` — فقط برای صاحب سفارش یا مدیر
- `GET /v1/admin/orders` — فقط مدیر

مرورگر اجازه ندارد مبلغ، ارز یا وضعیت پرداخت نهایی را تعیین کند. وب‌هوک باید امضا، تکراری‌نبودن رویداد و idempotency را بررسی کند و سپس سفارش را قطعی کند. اطلاعات کارت هرگز در سرور سایت ذخیره نمی‌شود.

درگاه‌ها پشت رابط یکسان `PaymentProvider` اجرا می‌شوند و مقدار `provider` یکی از گزینه‌های فعال و مجاز پنل است. درخواست ایجاد پرداخت باید هدر `Idempotency-Key` داشته باشد و سرور مبلغ و ارز را فقط از رکورد محصول در دیتابیس بخواند؛ نه از مقادیر ارسال‌شدهٔ مرورگر یا اپ.

## رسانه و مدل سه‌بعدی

- آپلود مستقیم از کاربر نهایی ممنوع؛ ابتدا URL امضاشدهٔ کوتاه‌مدت از بک‌اند دریافت شود.
- نسخه‌های WebP/AVIF، thumbnail و poster تولید شوند.
- مدل GLB/GLTF از نظر اندازه، تعداد polygon، texture و حق استفاده اعتبارسنجی شود.
- اپ باید نسخهٔ سبک یا poster را بر اساس قدرت دستگاه انتخاب کند.

## همگام‌سازی

- پاسخ‌های محتوا `version` و `updatedAt` داشته باشند.
- اپ از ETag یا `If-None-Match` استفاده کند.
- تغییرات مدیر با optimistic concurrency و `If-Match` از overwrite جلوگیری کنند.
- اعلان push فقط پس از رضایت کاربر و اتصال سرویس مجاز فعال شود.

## استقلال از دیتابیس

قرارداد بالا لایهٔ عمومی سایت و اپ است. بک‌اند باید Repository/Adapter جداگانه داشته باشد تا PostgreSQL، Supabase یا ارائه‌دهندهٔ سازگار بدون تغییر رابط سایت جایگزین شود. اتصال مستقیم مرورگر به هر دیتابیس مجاز نیست و کلیدهای مدیریتی فقط در سرور نگهداری می‌شوند.

## مدل‌های اصلی داده

`users`، `roles`، `projects`، `media`، `tutorials`، `insights`، `products`، `orders`، `payments`، `leads`، `subscribers`، `consents`، `audit_logs` و `content_versions`.
